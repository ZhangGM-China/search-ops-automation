## 1. 规则

- 相关性阶段对当前 Mixed 商品同时提供文本和图片信息，统一调用多模态模型判断。
- 图片 URL 直接作为模型图片输入；图片失败或不可解码时记录警告，模型仅依据文本判断。
- `brand + query + product_id` 已有相关性通过记录时永久复用，不再调用模型；只有通过记录可用于跳过检测。
- 相关性综合品牌商品文本和图片判断整体搜索意图，不分别要求图文通过，不机械采用任一方否决。材质成分、功能参数依据文本；风格、元素、图案、颜色、版型等结合可观察的图片特征。标题未提及不等于不具备；关键条件明确不符或综合证据后仍无法确认时判不相关，后者必须说明“无法确认”，不得编造相反事实。图片缺失本身不是不相关原因。多个款式中至少一个完整满足条件即可相关，不拼接不同款式的属性。是否自动拉黑仍取相关性 Agent 与 `product_blacklist` 的最严格执行模式。
- 所有已判定不相关的商品在检测完成后立即独立进入拉黑处理，复用受控网关、幂等、审计和权威回读，不依赖根因分组、商品详情补齐或 KG 方案生成。相关性 Agent 模式与 `product_blacklist` 模式取最严格：`disabled` 禁止写入，`human_approval` 保存待确认动作，只有两者均为 `auto` 时自动拉黑。未能判定不相关的商品不进入该集合。拉黑失败仍投递根因任务，根因任务失败不影响已完成的拉黑事实。

## 2. 规则维护

用户取消拉黑时可填写理由。取消理由只作为审计记录（记录商品、操作人和时间，可在“相关性规则”页底部查看），不写入相关性规则。相关性规则只能由用户手动填写：在“相关性规则”页编辑保存、追加单条规则，或在纠正弹窗中“纠正并取消拉黑”时填写的纠正规则。每次模型检测加载当前规则作为系统提示词。

治理方案内每张错误商品卡片展示已拉黑或未拉黑状态，并提供纠正及拉黑状态操作。卡片上的拉黑与取消拉黑直接提交并回读，不再打开纠正弹窗；纠正弹窗仅用于补充 Query 相关性检测规则，可悬停查看当前规则。错误商品支持勾选后批量拉黑或批量取消拉黑。纠正弹窗中“纠正并取消拉黑”填写的纠正规则与取消动作在同一次受控请求内提交并回读；其它取消拉黑入口不写规则。新规则追加到该品牌与 Query 既有规则末尾，使用连续数字编号。取消拉黑继续通过受控动作、审计和权威回读完成。

提交相关性规则时，系统在保存前过滤无法写入规则库的特殊字符，保留其余文字、标点和换行。追加规则过滤后若没有有效内容，提示输入有效规则。

## 3. 根因分析与分组

根因 Agent 以“一个 Query 的全部错误商品”为单次输入，在商品集合内按根因分组，而不是为整个 Query 只生成一个结论，也不是逐商品重复调用 Agent。同一 Query 可同时得到：

- 一个或多个“个例”原因组，结论统一显示“个例，需拉黑”，不再生成重复的拉黑动作；商品是否拉黑由独立流程决定。
- 一个或多个“知识图谱问题”原因组，每组独立生成一套可执行 KG 方案。
- 证据不足或原因冲突的分组，进入人工确认，不由系统猜测执行。

Agent 输入包含品牌、原始 Query、Query 分词及命中的 KG 标签、错误商品列表、商品标签与推理链路、相关性判断原因，以及 Query 标签的标签信息、双向关联标签和关系类型。检测后先按两层有效模式处理全部不相关商品的拉黑，再独立投递根因分析；根因分析只生成 KG 修复动作，商品详情缺失只影响根因确认，不阻断既有检测结论的拉黑。

## 4. 结构化 KG 方案与执行

KG 问题组不能只输出自然语言建议。每套方案由模型输出原因组、有序 `actions`、完整动作参数、步骤依赖和简短依据；系统生成展示标题并管理执行状态、审计、执行前快照和回滚记录。受控动作只使用真实接口契约中的新增/更新/拉黑标签、新增/更新/删除关系六类；合成词、二次分词和谐音通过标签属性表达。

- 每套 KG 方案取所属 Agent 与全部涉及的 KG 工具中最严格的执行模式；混合标签和关系动作不能绕过其中任一工具的限制。自动模式下，每个原因组方案生成后立即进入受控执行，不等待其他 Query。
- 确认模式下，每套方案提供独立的“一键执行”，人工确认后使用同一受控执行器；自动任务不能调用确认模式方案。禁止模式不提供执行入口，执行器也禁止写入。
- 执行器负责执行前 KG 状态和参数校验、按依赖顺序执行、幂等与审计、权威回读和回滚记录。

拉黑和 KG 动作均复用[统一状态与动作契约](统一状态与动作契约.md)，不新增另一套页面状态。

## 5. 统一重新打标签与验证

- KG 方案的执行与重新打标签分开：方案在各原因组就绪后可立即执行，重新打标签不随每套方案频繁触发。
- 系统按“品牌 + 治理日”聚合批次；当日所有 Query 中需执行的 KG 调整都进入已执行、已取消或明确失败等终态后，统一触发一次全量重新打标签。同一品牌治理日最多触发一次。
- 重新打标签触发后等待 30 分钟再验证：错误商品是否消失、正确商品是否被误伤，并记录验证前后召回数量和最终结论。
- 验证结果展示在执行概览的“相关性”卡片，不放入治理方案卡片。
- 相关性治理方案支持“纠正验证”：用户可对当前 Query 单独发起一次异步相关性检测，验证新增纠正规则是否被检测 Agent 吸收。结果在“纠正验证”弹窗中按错误商品、正确商品顺序展示；执行状态仅回显在按钮文案下方的最近验证时间，不改变拉黑、KG 或主治理状态。

## 6. 前端展示

- 同一 Query 按根因归纳为“策略 N”，每个策略依次展示策略标题、执行步骤、错误商品数量和本组商品列表。多个策略各自带自己的商品，不再把商品合并到所有策略之后。
- 知识图谱策略标题右侧展示执行状态和“一键执行”，仅执行该策略中的步骤；没有可执行步骤时展示需人工复核。个例策略显示“个例，需拉黑”，不提供知识图谱执行按钮。策略执行状态与商品是否已拉黑分别展示。
- 知识图谱步骤按顺序编号，使用“创建标签：羊毛”“创建标签关系：羊毛从属于材质”“创建标签关系：羊毛同义于羊绒”“删除标签关系：羊毛从属于羊”等动作文案。仅使用已有动作能力，不增加删除标签能力。
- 步骤中的标签可点击打开属性弹窗。只展示：标签名称、展示名称、根标签（是/否）、维度信息、权重、英文分词（是/否）、二次分词（是/否）、合成词（是/否）、合成词的包含词、合成词的排除词。创建标签展示准备创建的属性；关系两端可分别查看并在弹窗切换。读取失败明确提示并支持重试，不推断缺失属性。
- 各策略下“错误商品（数量）”右侧提供批量拉黑或取消拉黑，以及纠正验证；操作仅针对本组商品。首次选择商品后，只能继续选择相同拉黑状态的商品，批量操作期间显示加载状态。同一商品已有原因组时只在原因组展示一次，不展示原始拉黑参数、重复列表或分析依据折叠区。
- 执行概览“相关性”卡片展示检测商品数、错误商品数、拉黑状态、根因分组数、KG 策略执行状态、重新打标签状态、验证时间、误召回与误伤结果、验证前后召回数量和最终结论。

## 8. 验收场景

- Given 文本未提及某个视觉特征但图片可明确支持，When 综合判断满足 Query 的关键条件，Then 商品判相关，不要求文本重复证明。
- Given 材质或功能条件在可用文本中无法确认，When 检测完成，Then 判不相关并说明“无法确认”，不得凭图片猜测成分或编造相反事实。
- Given 图文看似冲突，When 检测执行，Then 先核对商品、款式和属性，再根据适合判断该属性的证据形成结论，不机械采用图文一票否决。
- Given 至少一个款式完整符合 Query，When 检测完成，Then 判相关；不同款式分别满足部分条件不能拼成相关结论。
- Given 商品关键条件明确不符，When 检测完成，Then 按相关性 Agent 与 `product_blacklist` 的最严格模式处理拉黑并保存证据，不等待根因分析。
- Given 图片不可用，When 检测完成，Then 记录图片警告并仅依据商品文本判断；判定不相关时仍按两层最严格执行模式处理拉黑。
- Given 同一 Query 有多个错误商品且包含不同根因，When 根因 Agent 完成，Then 一次输出多个商品原因组，个例组显示“个例，需拉黑”，每个 KG 问题组形成独立结构化方案。
- Given KG 问题组使用自动模式，When 该组方案生成，Then 立即执行该方案，不等待其他 Query 方案生成。
- Given 同一品牌治理日的 KG 调整已全部收口，When 统一触发重新打标签，Then 当日只触发一次，并在 30 分钟后把验证结果回显到执行概览“相关性”卡片。

- Given 相关性自动、拉黑自动、KG 确认，When 检测到不相关商品，Then 全部先自动拉黑并回读，KG 方案等待人工一键执行。
- Given 相关性确认、拉黑自动，When 检测完成，Then 保存待确认拉黑动作且没有自动写入。
- Given 根因分析失败或部分商品详情缺失，Then 不撤销或阻断检测阶段已完成的拉黑。

### KG 领域与策略补齐

相关性根因分析采用 PRD-12 的共享领域知识、双向关系和维度只读查询；详情先由工程侧补齐再统一提供。KG 策略新增“拉黑标签”，沿用 kg_tag 执行模式与审计，并验证 isBlack=1；它不等同商品拉黑。保留现有原因分组和商品唯一归属。

### 策略生成失败处理

错误商品治理使用现有 PI Runtime 的独立任务上下文，通过只读 MCP 调查商品、标签、关系及维度；先调查分组，再选择治理方式。召回治理 Agent 不变。仅允许六类真实动作：新增/更新/拉黑标签、新增/更新/删除关系。JSON Schema 明确各动作完整字段及条件；不猜填业务参数，不再调用额外的 action-repair 模型。校验失败保留原始输出、查询证据和具体错误，展示人工复核。MCP 配置缺失或不可用时显式失败，不回退直连接口。空组不得执行其它组动作，商品拉黑状态独立保留。

品牌配置提供一个自由文本运营参考编辑框和保存按钮，记录修改人、修改时间。首次加载品牌适用的默认案例，保存后默认用于下一次错误商品 KG 任务；清空后保持为空。无启停、版本号、历史对比，参考不影响无结果、少结果及骤降治理。
