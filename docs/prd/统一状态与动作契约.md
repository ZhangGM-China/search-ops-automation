# 统一状态与动作契约

## 1. Top Query 节点状态

Top Query 节点只使用以下状态：

| 状态 | 含义 |
| --- | --- |
| 待执行 | 节点尚未开始 |
| 执行中 | 节点正在处理 |
| 已执行 | 节点处理完成 |
| 已跳过 | 按规则无需处理 |
| 异常 | 节点处理失败或关键事实不可用 |

节点状态、结果、错误说明和耗时及时落库；单个 Query 异常不阻塞其他 Query。

品牌页左侧检查项和详情页执行概览使用同一套检查项展示状态：一种状态对应一个标签和一种颜色，状态可以有多条触发条件；按“异常 → 待处理 → 未执行 → 需关注 → 正常”的严重度顺序取第一条命中。

| 展示状态 | 颜色 | 触发条件（命中任一） |
| --- | --- | --- |
| 异常 | 红 | 检查失败（failed / check_failed / error / 处理后仍有问题）；治理失败（failed / rollback_failed） |
| 待处理 | 黄 | 检查进行中（pending / running / executing / 待人工确认 等）；治理尚未收敛（待生成、执行中、需人工复核、结果待确认、回滚中） |
| 未执行 | 灰 | 检查跳过、取消或失效；没有检查记录（含断码没有巡检事实） |
| 需关注 | 蓝 | 检查已完成但检出业务问题（相关性不符、断码、需要重排序等）；治理已修复、已验证或已完成 |
| 正常 | 绿 | 检查正常完成、未检出业务问题且下游没有待办 |

治理已回滚或被拒绝时按问题证据判定：仍有问题证据视为需关注，没有问题证据视为正常。颜色只描述检查项的当前处置结论，不改写节点或动作的持久化状态；详情保留节点状态、问题证据与治理方案各自的状态和失败原因，治理方案卡片继续展示动作生命周期原状态。

## 2. 主链状态

主链固定执行“采集 S0 → 召回检查 → 排序治理 → 相关性检测 → 主链结束”。不使用 Planner、Evaluator、健康评分或 Agent Loop 状态推进。

## 3. 动作边界

动作必须经过权限、品牌范围、幂等、写后回读和审计。请求成功不等于动作已验证；回读失败记录异常并继续可执行的后续节点。

治理方案面向运营人员只展示以下状态：

| 展示状态 | 业务含义 |
| --- | --- |
| 待执行 | 方案已生成，尚未进入执行 |
| 执行中 | 治理动作正在提交或处理 |
| AI 已执行 | AI 生成或触发的方案已由系统自动执行并验证成功 |
| 手动已执行 | 人工触发的方案已执行并验证成功 |
| AI 执行失败 | 系统自动执行明确失败 |
| 手动执行失败 | 人工触发执行明确失败 |
| 结果待确认 | 动作已提交，但权威回读暂时不能确认结果 |
| 回滚中 | 已发起回滚，尚未确认完成 |
| 已回滚 | 回滚已经确认完成 |
| 回滚失败 | 回滚明确失败，需要人工处理 |
| 已取消 | 方案被人工取消或拒绝 |

执行方式和动作生命周期分开记录。成功或失败状态必须读取实际执行来源，不得只根据方案预设的 `auto` 或 `human_approval` 推断。失败原因和失败阶段属于详情信息，不新增为展示状态。

“执行失败”与“已回滚”不是重复状态：动作未生效或无可回滚变更时使用执行失败；部分步骤已生效且回滚经权威回读确认后使用已回滚。

相关性错误商品的拉黑动作复用同一契约。`auto` 表示自动提交，`human_approval` 表示人工确认后提交，`disabled` 表示只记录不执行；这些执行模式不扩展上述展示状态。相关性根因 Agent 生成的 KG 结构化方案也复用同一动作生命周期；其原因分组、重新打标签批次和 30 分钟后的效果验证属于业务事实，不新增页面动作状态。

## 4. 其他流程

- KG Agent 和相关性错误根因 Agent 是异步任务，Agent 任务状态向用户简化为待处理、已生成方案、异常；方案执行状态仍按第 3 节展示。
- 断码是独立周期任务，使用自身巡检和恢复记录，不进入主链节点状态。
- A/B Test 实验组执行完整主链，对照组只记录数据变化，不执行治理写动作。
