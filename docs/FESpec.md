# 前端开发规范

本文档规定 AIOPS 前端的工程实现、质量和验证约束，供人和 AI 在开发前共同遵守。视觉 Token、页面外观和组件样式以[设计规范](DESIGN.md)为准，本文件不重复维护颜色、字号、间距等视觉数值。

## 1. 阅读顺序与文档边界

开发或调整前端时，按以下顺序阅读：

1. [设计规范](DESIGN.md)：当前视觉基线、页面层级、状态呈现和组件外观。
2. `frontend/src/styles/index.css`、`frontend/src/app/theme.ts`：可直接复用的 Token、class 和 Ant Design 主题事实。
3. 当前 Feature 的相邻页面、组件和测试：确认既有交互、路由、权限和局部约定。
4. [整体技术架构](TSD/01-整体技术架构.md)：项目目录、运行边界和前后端职责。
5. [联调验证与证据边界](TSD/08-联调测试与规范.md)：当前可执行的门禁、E2E 条件和验证范围。

`DESIGN.md` 负责“界面应呈现什么样”，本文件负责“代码应如何组织、实现和验证”。接口字段、权限与受控动作的业务契约以 API、TSD 和当前代码为准，不由前端页面自行推断或改写。

## 2. 当前技术边界

- 框架：React 19，使用函数组件和 Hooks。
- 类型：TypeScript。当前编译配置尚未启用 `strict`；组件 Props、公开函数和 API 返回值仍必须使用明确的 `type` 或 `interface`，不得使用 `any`。
- UI：桌面端使用 Ant Design v6，移动端使用 Ant Design Mobile；不得因单页需求引入第二套 UI 或样式体系。
- 图表：当前项目使用已有 SVG 图表实现。新增图表优先复用现有实现；引入图表库或其他前端依赖必须先单独确认。
- 视觉实现：先复用 `DESIGN.md`、现有 Token 和 `.ops-*` class。动态尺寸、坐标或局部布局可以使用 inline style；不要在业务组件中散落可复用的颜色、字号、间距和圆角定义。
- 边界：前端只能通过既有 API 层访问系统能力，不直连生产数据源、搜索运营或知识图谱等外部系统。

## 3. 代码组织与职责

- 采用 Feature-first：业务页面、局部组件、Hook、类型、工具和资源优先归入所属 `frontend/src/features/<feature>/`；不为预期需求创建空目录。
- `app/` 放应用壳、路由、布局、主题和鉴权入口；`shared/` 只放至少被两个 Feature 稳定复用、且不依赖任一 Feature 的能力。
- 依赖方向为 `app → features → shared`。`shared/` 不得反向依赖 `features/` 或 `app/`；Feature 之间不得深层导入内部实现，需要复用时应通过窄的公共出口或下沉到 `shared/`。
- 300 行是职责评估触发线，不是自动拆分阈值。当前改动触及超过 300 行的页面、组件或 Hook 时，检查是否混合了独立业务职责、数据加载、列定义、图表配置或桌面/移动端视图；职责单一且可读时可保留，无须为此建立额外台账。
- 生产 UI `.tsx` 文件超过 500 行时默认按明确职责拆分。静态数据、fixture、纯类型和测试文件不适用；确有例外时，在当前代码评审中说明理由。
- 不为视觉调整改变业务文案、接口字段、权限规则、路由入口或受控动作链路。

## 3.1 Top Query 页面边界

- Top Query 页面展示两类商品：治理前 `S0` 快照和实时 Mixed 结果；`S0` 只读展示，不随治理动作覆盖。
- 页面按节点展示待执行、执行中、已执行、已跳过和异常；异常必须同时展示人类可读的说明。
- 主链只展示召回检查、排序治理和相关性检测。断码是独立周期任务，仍在 Top Query 页面展示多次巡检记录，不作为主链节点。
- 页面展示治理动作记录：拉黑、排序调整、断码降桶/恢复及其回读结果；不展示 Planner、Evaluator、健康评分或旧 Agent Loop 状态。
- KG Agent 方案、世界事实警告、相关性规则和模型配置以对应 API 返回为准；前端不自行推断或合并状态。

## 4. 实现质量与可访问性

- 列表或日志页有筛选需求时，默认使用“标题与说明 → 筛选 → 工具栏 → 数据区 → 状态区”的结构；桌面端通常使用小型 `Card` 和 inline `Form`，移动端可使用筛选 Popup 或抽屉。工作台、详情和智能助理可按任务流采用分栏、时间线或抽屉，不套用机械模板。
- 使用语义元素：页面和区块可使用合适的 `h1`、`h2`、`h3`，并通过现有 class 保持视觉一致；不要仅为统一样式而放弃标题语义。
- 可点击的导航或操作优先使用原生 `<a>` 或 `<button>`。只有确需使用非原生容器时，才补充合适的 `role`、`tabIndex`、键盘 Enter / Space 行为和可访问名称。
- 图标按钮必须有可访问名称；状态不能只依赖颜色，应提供清晰文字、必要的风险说明和进入详情或证据的入口。
- 每个请求区域都应明确呈现加载、空态和错误态；桌面端关键操作默认可达，移动端不得依赖无意义的水平滚动、文字重叠或溢出完成核心任务。
- 前端不得新增 Ant Design、Ant Design Mobile 或 React 控制台 warning。

## 5. 测试与验证

- 纯函数、Hook、组件和单页面 Vitest 测试与被测模块共置，使用 `*.test.ts` 或 `*.test.tsx`。
- 跨页面或跨 Feature 的 Vitest 集成测试放在 `frontend/src/test/integration/<scope>/`；目录与职责守卫放在 `frontend/src/test/architecture/`；浏览器 E2E 统一放在 `frontend/e2e/`。生产代码不得导入测试模块。
- 变更路由、登录、权限、关键受控动作流或移动端交互时，除相关 Vitest 外还应执行 E2E；其他变更按影响范围选择定向测试或前端门禁。
- 从项目根目录执行常规前端门禁：`ENV=test bash scripts/ci/test_frontend.sh`。需要浏览器验证时执行：`ENV=test OPENAI_API_KEY=test-key bash scripts/ci/test_e2e.sh`。完整前提、范围与故障含义以[联调验证与证据边界](TSD/08-联调测试与规范.md)为准。

## 6. 前端变更检查清单

- 已读取设计规范、现有样式和同 Feature 实现，未新建平行设计体系或未经确认的依赖。
- 新代码归属正确，`shared/` 满足稳定复用和依赖方向要求。
- 页面在桌面和移动端均可完成核心任务；加载、空态、错误态和受控动作反馈完整。
- 标题、按钮、可点击区域和状态信息具备正确语义与可访问性。
- 超过 300 行的受影响文件已完成职责判断；超过 500 行的生产 UI 已拆分或在评审中说明例外。
- 测试位置正确，已执行与改动风险相称的 Vitest、前端门禁和必要的 E2E。

## 7. 维护原则与相关文档

- 本文件仅保留长期、可复用且能指导实现或验证的规则；一次性问题、历史记录和任务细节不写入本规范。
- 视觉变化先更新[设计规范](DESIGN.md)及其权威样式实现；目录或运行架构变化更新[整体技术架构](TSD/01-整体技术架构.md)；测试入口与证据变化更新[联调验证与证据边界](TSD/08-联调测试与规范.md)。
