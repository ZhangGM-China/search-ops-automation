## 1. 文档定位与边界

本文记录跨模块的运行安全边界：环境选择、受控业务动作、补跑与健康排查，以及发布和回滚的分层关系。

- 业务流程和状态机以[业务流程与状态流转](02-业务流程与状态流转.md)及模块技术设计为准。
- 调度注册、并发、lease 和恢复机制以[调度与中间件](06-调度与中间件.md)为准。
- 写接口的权限、幂等、权威回读和未知结果以[内部写入与执行契约](api/04-内部写入与执行契约.md)为准。
- 生产发布的操作步骤以[生产发布指南](../production_deployment_guide.md)为唯一契约；[联调测试与规范](08-联调测试与规范.md)定义验证证据层级。

本文不以历史归档、静态代码或局部测试推断某环境已经发布、切流或验收通过。

## 2. 模式与安全边界

以下四层彼此独立，不能互相替代：

| 层级 | 当前控制项 | 解决的问题 | 不代表什么 |
| --- | --- | --- | --- |
| 运行环境 | `ENV=test`（默认）/ `ENV=prod`（显式） | 选择本地治理库和外部服务环境；搜索运营适配层会阻止 `test` 向已识别的生产地址写入。 | 不是业务 dry-run，也不授权生产操作。 |
| 业务执行 | No Result 的 `dry_run / real_write`、`human_approval` | 决定仍保留模块的治理动作是否真实执行，或是否必须人工确认；Top Query 不保留 dry-run。 | 不是版本灰度或生产发布。 |
| 应用发布 | TKE 候选 `standby`、激活 `active`、受控蓝绿槽位 | 隔离候选工作负载并切换应用版本。 | 不等于客户流量已切换。 |
| 客户流量 | 外部 HTTPS / DNS / 代理映射 | 将客户入口指向已验收的应用。 | 不由应用发布脚本自动修改。 |

`ENV=prod` 只表示选择生产配置，不授予外部写、schema 迁移、Git push 或生产发布权限。任何外部写结果不确定时，先按接口契约只读核查或人工收口，不得以重试代替确认。

知识图谱是环境路由的明确例外：KG 没有独立 STG 场景，ATLAS、HARBOR、Riviera 和 Lumen 的 `sceneId` 配置无论 `ENV=test` 还是 `ENV=prod` 都从正式业务地址读取；搜索、商品等其他业务接口仍按 `ENV` 切换。该配置读取不代表授权执行 KG 写操作。

## 3. 兼容性边界

| 已退役入口 | 当前行为 | 替代入口 |
| --- | --- | --- |
| `/task-board` 及其 API | 前端不再注册，API 返回 `404`，不做转发。 | `/ops-dashboard` 与当前 Query 治理页面。 |
| `/manual-attention` | 前端不再注册，不做转发。 | 当前治理工作台和动作待确认链路。 |

兼容性变更先更新[接口设计](04-接口设计.md)，并同步维护退役入口测试；不要在新功能中恢复旧路由或旧权限映射。

## 4. 恢复与补跑

Top Query 的统一运维入口是新治理批次和 Checkpoint 服务。`run_agent_loop_rerun.py`、`resume_agent_loop_rerun.py` 和 `report_top_query_batch_anomalies.py` 属于旧 Agent Loop 入口，已退役；新文档和新自动化不得依赖它们。

主链单次执行预算耗尽后以 `running` 和 `invocation_yielded` 留下完整批次，恢复每五分钟继续；这与 Query 的 `budgetStop` 是不同状态。恢复不会补建未创建的历史品牌日期。历史补跑必须明确 brand/data_date、源数据可用性、当前配置指纹，以及是否复用已有冻结 selection；创建缺失批次可能与当日原本选样不同。沿用 `query_governance_mainline_job(brand_filter, target_date, ...)` 业务入口并受 Scheduler leader fence、品牌锁和 ActionGateway 约束，不裸调用 workflow 或退役脚本。

生产验收分别检查容器无 OOM、leader/状态新鲜度、所有启用品牌的批次或明确跳过、checkpoint 真实推进，以及外部动作权威回读。Pod Ready、调度 Job 成功、`resumedCount` 单独一项都不能代替业务验收。图片压缩后的 768 像素不能反推解码峰值；完整生产负载的内存峰值和连续日调度窗口需在发布后记录。生产发布、品牌重新启用和历史业务补跑均须明确授权；代码回滚不自动撤销成功的外部动作。

| 场景 | 安全处理 | 禁止做法 |
| --- | --- | --- |
| 快照差异或需重建任务 | 先使用快照校验；重建走受控 `snapshot/rebuild` 接口，遵守品牌权限、请求身份和权威回读。 | 直接修改任务或绕过动作链重建。 |
| 已停止的预算或失败工作流 | 从持久化 checkpoint 和代码声明的安全节点判断；`budgetStop` 不重新消费 LLM 或重复执行动作。 | 默认从头重跑。 |
| `execution_unknown` 或外部写超时 | 保留请求身份，先做权威 readback / reconcile；无法确认则人工处理。 | 直接重发外部写请求。 |
| 补跑与定时任务可能重叠 | 先检查 Scheduler 状态、任务会话、workflow run 和最近表活动；`superseded` 尾单不恢复。 | 只按运行时长认定卡死，或并行推进同一范围。 |

快照接口见[Query 治理接口](api/06-Query治理接口.md)，动作失败处理见[内部写入与执行契约](api/04-内部写入与执行契约.md)，调度恢复实现见[调度与中间件](06-调度与中间件.md)。项目外历史归档只可作为背景，不是当前操作或验收事实源。

## 5. 健康检查与排查顺序

`/api/health` 的单个汇总字段不足以判断业务健康。先只读核对以下事实，再决定是否补跑、恢复或升级处理：

| 排查面 | 首要事实源 | 判断边界 |
| --- | --- | --- |
| API 与运行时 | `/api/health`、API startup/readiness 状态 | HTTP `200` 不能单独证明 Scheduler 或业务任务正常。 |
| 调度与任务 | `scheduler_job_run`、`task_run_session`、Scheduler 状态 | 长跑任务仍有 workflow 或表活动时，不应仅按耗时判为 stale。 |
| 数据与工作流 | `top_query_workflow_run`、相关业务表活动 | checkpoint 损坏或安全状态不明时转人工，不盲目恢复。 |
| 外部依赖 | `operation_log`、错误率、P95、受控日志 | 外部抖动优先降级、dry-run 或人工确认，不把请求已发送当作成功。 |

`service_health_check_job` 负责综合 API、数据库新鲜度、外部只读探针和性能检查；具体注册与恢复规则仍以 06 为准。

## 6. 回滚与发布边界

运行镜像的依赖使用 `requirements.lock` 的版本及哈希固定。2026-10-07 的供应链修复将 LangGraph/SDK 更新至兼容的修复版本、zlib 更新至 `1.3.2-r1`；后端仅从 Alpine 官方 edge 引入固定的 Expat `2.9.0-r0`，并用同版本 CPython 的源码（SHA-256 校验）重建 `pyexpat` 与 `_elementtree`，防止 Python 继续使用内嵌旧库。编译工具和头文件在同一层删除。前端将 PCRE2 更新至 `10.49-r0`；不加载可选 Nginx 模块，因此移除这些模块及其 XML/图片处理依赖，删除旧 libxml2 豁免。发布前须对实际镜像执行 `verify_runtime_security.py`，验证 XML 解析兼容性及 SDK 的 actions 授权范围，并通过无临时豁免的供应链扫描。

| 范围 | 当前能力 | 边界 |
| --- | --- | --- |
| 业务治理动作 | Top Query 动作回滚；No Result 批次/Query 回滚。 | 必须按动作类型做权威回读；`execution_unknown` 不能自动重放。 |
| 运行配置 | 配置更新有受控写入与回读；节点模型配置有版本回滚，Ops Team Prompt 已退役。 | `save_config()` 的 bind mount 回退写只是持久化兜底，不是通用 YAML 版本回滚。 |
| 应用版本 | 已有受控蓝绿发布和 `tke-rollback`，只回退到记录的前一个不可变 release。 | 不是自主触发的自动灰度平台；每次操作仍需明确授权。 |
| schema 与业务数据 | 不属于 TKE 应用发布链。 | 需要独立方案、备份/恢复边界和单独授权。 |

生产发布统一使用 `scripts/release/release.py`：先用 `tke-preflight` 快速检查本地物料、Docker 与目标集群前置条件，再执行 `tke-candidate`、`tke-prepare`、`tke-rehearse-pull`（`cluster pull`）、`tke-rehearse-mysql`、`tke-rehearse-deploy`、`tke-rehearse-accept`、`tke-activate`、`tke-accept` 与 `tke-rollback`，各阶段证据必须绑定同一 release SHA。入口把安全的阶段开始、结束、耗时和失败分类写入独立状态文件。`tke-pipeline` 仅按相同阶段编排执行，默认停在无流量 standby；只有显式指定 activate 才继续激活。候选 Scheduler 为 `standby`，激活后为 `active`；客户流量切换另行确认。完整步骤见[生产发布指南](../production_deployment_guide.md)。
