## 1. 文档定位与边界

本文定义定时任务的注册、运行控制、可靠性恢复，以及 API 的实际 HTTP middleware 与启动运行时边界。

- 业务工作流和模块内部状态分别以[业务流程与状态流转](02-业务流程与状态流转.md)及对应模块技术设计为准。
- 表结构、接口契约、发布/运行操作和测试执行分别以[数据存储设计](03-数据存储设计.md)、[接口设计](04-接口设计.md)、[运行、恢复与发布边界](07-兼容性灰度与运维.md)、[联调测试与规范](08-联调测试与规范.md)为准。
- 本文不把框架依赖清单、发布命令或一次性验证结果当作调度设计。

## 2. 调度运行架构

```text
main.py
-> 生产环境 schema 校验 + release identity 读取
-> start_scheduler()
   ├-> standby：仅上报 ready，不创建 APScheduler、不获取 leader lease、不执行业务任务
   └-> active：本地进程锁 -> 数据库 leader lease + heartbeat + fencing
               -> BlockingScheduler + fenced jobs
               -> 持久化 scheduler_job_run
               -> 终止排空、释放 leader lease
```

- `main.py` 传入稳定的 scheduler 名称、release identity 和配置指纹；生产环境先校验受控 schema。
- 进程锁防止同一启动入口重复运行；跨进程/跨实例的唯一 leader 由数据库 lease、心跳和 fencing token 保证，不能只依赖本地锁。
- 每个注册 Job 都通过 `SchedulerRunExecutor` 的 fenced 包装执行，运行事实带有 job slot、幂等身份、release 和配置指纹。
- `standby` 是候选运行模式：进程可就绪，但不得注册或执行生产业务 Job。

## 3. Job 目录

以下目录只描述 `active` 模式下由 `start_scheduler()` 注册的 Job。除特别说明外，均受 fenced 执行、持久化运行事实和 misfire 容忍约束。

| Job ID | Trigger / 默认频率 | 注册条件 | 职责 |
| --- | --- | --- | --- |
| Query 治理主链任务（新入口） | cron，按治理日任务配置 | 启用品牌 | 固定执行 `S0 → 召回检查 → 排序治理 → 相关性检测`；不使用旧 Agent Loop 或 dry-run。 |
| `atlas_ops_team_market_intelligence_job` | — | 已退役 | 不再注册 Ops Team 市场情报任务。 |
| `atlas_ops_team_brand_intelligence_job` | — | 已退役 | 不再注册 Ops Team 品牌情报任务。 |
| `no_result_governance_extract_job` | cron，每日 01:30 | 全局 `no_result_agent_enabled=true` | 抽取无结果 Query；实际品牌还须 enabled 且 `no_result_governance_enabled=true`。 |
| `no_result_governance_process_job` | interval，默认 15 分钟 | 全局 `no_result_agent_enabled=true` | 推进无结果词治理循环。 |
| `query_demotion_verification_job` | interval，1 分钟 | 始终注册 | Query 降桶验证/回滚，并对不确定动作和过期 lease 做 reconcile。 |
| `service_health_check_job` | interval，默认 60 分钟 | 始终注册 | 综合健康检查与受控告警。 |
| `operation_log_retention_job` | interval，10 分钟 | 始终注册 | 分批清理 operation log；测试环境保留 7 天，其他环境保留 30 天且不跨当月。 |
| `service_health_check_startup` | date，启动约 10 秒后 | 每次 active 启动 | 尽早刷新健康状态。 |
| `inventory_monitor_config_sync` | interval，1 分钟 | 始终注册 | 热更新品牌断码监测 Job；断码任务独立于 Query 主链。 |
| `query_governance_summary_reconciliation_job` | interval，5 分钟 | 始终注册 | 在最近 180 天内扫描已完成或带错误终态、但缺少批次摘要、缺少 Query 列表筛选索引或质量指标版本落后（`qualityMetricsVersion`）的工作流，并幂等回填摘要；单批失败不阻断其他批次。 |
| `query_governance_recovery_job` | interval，5 分钟 | 已提供主链 workflow factory | 兜底恢复超过 30 分钟无心跳的 running 批次，以及进程终止、租约失效后遗留的主动分段；保留品牌开关、互斥和 fence。 |

代码中存在的兼容入口或可手动调用函数不等于已注册 Job；实际注册事实以 `start_scheduler()` 为准。

## 4. 动态任务与模块内编排

- 普通动态治理以 `batch.selected` 判断是否启动；空选中集由选词服务直接返回空运行结果，调度返回 `skipped / no_candidates`，保留批次和数量。A/B 实验走独立实验调度器，固定样本与分组语义不变。
- 主链完成候选批次后，按品牌 `query_governance_candidate_history_days` 配置为选中 Query 物化 `[候选日-N, 候选日+N]` 的真实按日 PV/UV/点击 UV/ATC UV/购买 UV；快照按品牌、Query、日期幂等更新，源数据缺失时不补写 0。详情读取不再受任务日期截断。
- Read API 合并选词批次和 Query 任务选择最新数据日；选词记录存在、无入选或实验候选、无任务且无工作流运行记录时，展示正常跳过。已有工作流错误不能被空选词覆盖；没有选词/任务记录仍为无批次。无需新增表或迁移。

- 启动时会为每个 enabled 品牌注册 `broken_rate_monitor_job`，频率来自 `top_query_inventory_check_interval_minutes`；配置同步任务每分钟根据 enabled 品牌和 interval 新增、替换或移除动态 Job。断码 Job 使用 `coalesce=True`、`max_instances=1`，漏跑只合并为一次补跑，长任务期间不允许并发实例。
- 运行中的品牌 A/B 实验复用新的 Query 治理主链：实验组执行完整治理，对照组只记录自然数据变化。
- Ops Team/专家排序已退役，不再由 Scheduler、QueryDetail 或人工确认触发。
- 不得因看到某个函数定义就推断它会定时运行；需同时检查注册位置、模式、全局开关和品牌级开关。

## 5. 可靠性、恢复与终止

- scheduler leader lease 的 heartbeat 失效或 fencing token 过期后，旧实例不得继续写入任务结果。
- 每个 Job slot 先持久化、再 claim、执行、heartbeat 和终态收口；无法确认的中断结果为 `execution_unknown`，而非自动重跑。
- 启动时会恢复陈旧的运行事实，并为漏跑 slot 生成有上限、带幂等身份的补偿计划；计划持久化不等于未经授权地立即执行补偿。
- Query 批次完成事实与摘要物化是两个独立事实；摘要补偿任务只处理 `completed/error` 终态，不处理 `running/execution_unknown`，并通过唯一批次/品牌摘要记录保证重复执行安全。
- 终止时停止接受新任务、暂停 Scheduler、等待活跃任务排空，再释放 leader lease。排空超时必须失败收口，不能静默交接。
- API 健康状态、scheduler 状态文件和业务任务会话是不同事实源；HTTP 200 不能单独证明 scheduler 已接管或业务 Job 已完成。
- 生产入口遇到旧 leader lease 尚未到期时最多等待 90 秒，保持未就绪，不强抢租约；启动拒绝分别记录 `process_lock_busy` 和 `leader_lease_busy`。
- leader 心跳成功刷新进程状态；续租失效时停止接收任务、清除 ready，并通过幂等终止控制器排空。主线程返回前也等待排空；节点开始、节点结果持久化和外部动作调用前检查当前 fence。
- Scheduler 自身运行目录为 Pod 本地 `/tmp/aiops-scheduler`，状态含 `pid`、`updatedAt`。readiness 要求 PID=1 且状态小于 60 秒；liveness 要求当前进程、非失败状态且小于 180 秒。standby 每秒刷新状态，不创建业务 Job。
- 品牌主链与恢复共享 `TOP_QUERY_TASK_LOCK_DIR` 中的同品牌非阻塞锁；主链从第一片段持锁到该品牌终态或停止，品牌轮转期间保留锁，避免恢复扫描抢占健康的主动续跑。调用异常时统一释放；文件锁释放保留 inode。商业接口共享限流目录保持共享。
- 断码巡检执行降桶/恢复动作时会以阻塞方式持有同品牌锁（含外部网关回读，上游超时会拉长持锁时间）。主链抢锁改为有界等待：默认最多等 `QUERY_GOVERNANCE_BRAND_LOCK_WAIT_SECONDS`（1800 秒，env 可调），每 `QUERY_GOVERNANCE_BRAND_LOCK_POLL_SECONDS`（默认 30 秒）重试一次，等待与放弃各记一条 WARNING；等待失败才按 `batch_busy` 跳过该品牌当天批次。恢复任务固定传 `brand_lock_wait_seconds=0` 保持即时跳过，不排队在活跃主链品牌之后。
- 主链异常跳过（batch_busy、scheduler_stopping 等，brand_disabled 除外）会记 WARNING，并以 `skippedBrands`（如 `harbor:batch_busy`）写入 job 结果与 `scheduler_job_run.terminal_summary` 的 ` skipped=` 后缀，供事后直接从运行表定位丢品牌原因。
- 每次主链推进默认最多开始 100 个节点、240 秒，在新节点前检查预算；已发出的请求不会被强制终止，单次实际耗时可能超过预算。完整 Query 顺序、阶段屏障保留，分段结束 CAS 写入 `invocation_yielded=true`，不将批次提前标为 completed。同一 scheduler 运行内按品牌轮转立即消费该标记并继续冻结的选样；不重新提取候选、不重新物化指标、不重复读取控制组。关闭请求或 fence 丢失会在下一节点前停止续跑；无终态节点进展时停止轮转，5 分钟恢复任务仅作为故障兜底。
- 续跑在每个阶段先按批次一次性读取检查点节点状态，再决定本片段要开启的 Query；写入节点结果后只刷新对应阶段的批量读取缓存，避免对每条 Query 建立串行数据库读取。该优化不改变节点预算、阶段屏障、动作幂等或恢复语义。
- 恢复扫描通过 JSON 布尔的字符串表示兼容 SQLite/MySQL。只有目标 brand/batch 的真实终态节点数增加或 workflow 收口才计入 `resumedCount`；关闭、占用、无进展分别记入跳过/无进展明细。
- 此恢复仅扫描已有工作流，不自动补建历史缺失品牌日期；历史补跑需源数据预检、精确清单和受控动作授权。

## 6. HTTP middleware 与运行时边界

| 能力 | 当前实现 | 边界 |
| --- | --- | --- |
| CORS | `src/api/app.py` 的 `CORSMiddleware` | 仅定义允许的前端来源和请求方法/头，不替代认证授权。 |
| API lifespan | `src/api/lifecycle.py` | 启动时初始化测试环境数据，生产环境验证 release schema，并维护启动就绪状态。 |
| 读缓存 | `src/api/shared.py`、`src/api/redis_cache.py` | 优先使用 Redis JSON 共享缓存；未配置或不可用时回退进程内短 TTL cache。品牌总览与 Query 列表按权限/品牌、业务日期、页码和筛选条件隔离，当天 30 秒、历史日期 300 秒；实时结果按品牌、Query 和展示条数隔离，成功结果 30 秒、失败结果 5 秒。 |
| 外部请求治理 | `src/integrations/business_http.py`、`operational_service.py` | 限流、重试和熔断属于外部系统适配层，不是 FastAPI middleware。 |

当前没有消息队列、独立事件总线或分布式任务系统。Redis 仅承担只读 API 缓存，不承担任务编排、锁或业务状态存储。

## 7. 实现定位与 Change Map

| 变更目标 | 主要入口与联动检查 |
| --- | --- |
| Job 注册、频率、全局/品牌开关 | `main.py`、`src/scheduler/runner.py::start_scheduler`、`tests/test_scheduler.py` |
| leader lease、fencing、运行事实、补偿或恢复 | `src/scheduler/recovery.py`、`src/scheduler/reliability.py`、`src/persistence/repositories.py`、`tests/test_scheduler_leader_lease.py`、`tests/test_scheduler_job_run*.py`、`tests/test_scheduler_runtime_recovery.py` |
| 终止与排空 | `src/scheduler/termination.py`、`tests/test_scheduler_termination.py` |
| CORS、API 启动或就绪状态 | `src/api/app.py`、`src/api/lifecycle.py`、[接口设计](04-接口设计.md) |
| 外部限流、重试或熔断 | `src/integrations/business_http.py`、`src/integrations/operational_service.py`、[整体技术架构](01-整体技术架构.md) |

修改任何调度行为后，先判断其影响的是“注册、执行事实、恢复、业务工作流还是运行操作”，再进入对应全局文档和测试；不要把本地后台进程、测试运行或发布验收混为同一证据。
