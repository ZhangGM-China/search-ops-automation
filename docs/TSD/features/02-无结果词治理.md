## 1. 模块定位与边界

本模块负责无结果 Query 的抽取、去重、诊断、写入计划、受控执行、复核与恢复。

- 它拥有独立的批次和 Query 治理状态，不复用 Top Query 工作流作为唯一事实源。
- Agent 可以查询图谱和生成计划，但不能直接调用生产写接口。
- Top Query 的日任务、品牌 A/B 实验和 Ops Team 排序不属于本模块；它们只通过全局权限、动作网关和数据事实协作。

## 2. 上下文与协作关系

```text
生产只读数据源
-> 无结果批次与 Query
-> 图谱诊断与写入计划
-> 系统执行器 / 人工确认
-> retag、召回复核与运营工作台
```

- 批次抽取和治理循环可由独立调度任务触发；是否注册由全局调度配置决定。
- 写入、回滚和复核会调用受控外部系统；数据、接口和运行规则分别以[数据存储设计](../03-数据存储设计.md)、[接口设计](../04-接口设计.md)、[运行、恢复与发布边界](../07-兼容性灰度与运维.md)为准。

## 3. 方案概览

| 组件 | 设计职责 |
| --- | --- |
| 归一化与批次服务 | 过滤、去重、排除词和忽略 TTL，避免同一 Query 反复进入治理。 |
| 图谱诊断与计划生成 | 分词、查询图谱、诊断根因，并形成结构化写入计划。 |
| 执行器 | 按风险、执行模式和人工确认状态串行推进 Query 的动作。 |
| retag 与召回复核 | 在治理后执行后续标签处理和搜索结果复核。 |
| 运营工作台 | 展示批次、Query、动作、执行进度和人工操作结果。 |

## 4. 核心流程与状态

1. 从只读源抽取无结果 Query，`normalize_rows()` 完成归一化、去重和 TTL 排除。
2. `create_batch_from_records()` 创建批次与 Query。
3. Query 依次经过 `pending_context`、`pending_diagnosis`、`pending_graph_fix`，形成写入计划。
4. 动作按风险和执行模式进入执行或 `pending_execute`；同一 Query 的动作串行推进。
5. 执行后进入 retag 和召回复核；执行进度对外收敛为 `running`、`paused`、`completed`、`blocked` 或 `idle`。

## 5. 关键技术决策与不变量

- 采用独立治理状态，而不是把无结果问题强行塞入 Top Query 的治理语义。
- 工具严格分为 `query`、`write_plan`、`execution`：只读事实、计划生成和真实执行不能混用。
- 同一 Query 串行执行，以便每一步都能基于前一动作结果决定是否继续或恢复。
- 忽略 TTL 与动作指纹用于抑制重复治理；retag 与召回复核是后续质量环节，不是写入成功的替代证明。

## 6. 异常、安全与质量边界

- `dry_run` 或生产写未授权时，写动作保持 `pending_execute`，不得伪装为成功。
- `pause` 同时依赖持久化状态和运行时暂停集合，防止当前循环继续推进。
- 回滚、审批、执行和复核都必须经过品牌范围、权限、幂等、权威回读和终态收口。
- 风险超过允许范围或图谱证据不足时，动作必须等待人工确认或停止，不得越权执行。
