# Harbor 商品图错配（错图污染）：根因、修复与防复发报告

- 日期：2026-10-13
- 触发：品牌总览 →「马甲」Query 详情里，两件错误商品（西装马甲 SPU 1328942002、汗布马甲 SPU 1323994001）的缩略图都是同一张蓝色牛仔短裤图；用户进一步发现「商品详情弹窗里的图却是正确的」。
- 产出分支/worktree：`fix/harbor-image-repair` → `.worktrees/harbor-image-repair`
- 影响面：Harbor；生产库 914 条图片资产记录、390 个任务的商品快照、73 个治理计划，覆盖 4468 个商品。
- 状态：生产数据已全量修复并校验通过（verify = PASS）；防复发守卫已实现并通过离线测试。

## 1. 结论速览

1. **错图来自搜索索引，不是来自品牌目录，也不是我们取错字段。** 异常窗口内，`POST /api/search/mixed`（搜索索引）返回的商品行 `mainImage` 被写成同一张图
   `https://asset.harbor.example.test/media/catalog/product/f/a/fae7537d5904011483cc1bd867f13b0432a5a1c1_xxl-1.jpg`（蓝色牛仔短裤，2333×3500，2009448 字节）。
2. **这条链路只做透传**：`product_adapter._image_value()` → S0 快照 → 相关性候选 `blacklist_candidates` → 治理计划 `request_json.product_images` → 前端缩略图，全程如实使用索引给的 URL。
3. **详情弹窗走的是另一个接口**：`POST /admin-api/search/product/list`（品牌商品目录），该接口全程返回正确图 —— 所以「卡片图错、点开对」是两条数据源的差异，不是前后端 bug。
4. **模型没有幻觉**：它看到的确实是牛仔短裤图（候选里 `image_checked=true`），「图片显示的是牛仔短裤，不是马甲」是对错图的正确描述；错的是图。
5. **索引现已自愈**：2026-10-13 复测 prod/test 两个搜索环境，该错图 URL 均为 0 命中；索引在 2026-10-12 19:04Z 前后被批量重刷，恢复正常。
6. **我们做的事**：①按用户授权全量清洗生产库里的错图痕迹（不重跑历史相关性检测）；②新增「共享图守卫」，让同类错图不再进入图片判断；③提供可重复运行的盘点 / 修复 / 校验 / 回滚工具与前置备份。

### 2.2 为什么「卡片图错、详情图对」

| 页面元素 | 接口 | 数据源 | 当时状态 |
| --- | --- | --- | --- |
| 治理方案卡片缩略图 / 相关性判图 | `POST /api/search/mixed` | 搜索索引商品文档 `mainImage` | ❌ 被写入错图 |

### 2.4 排除项（都验证过）

- **不是我们取错字段**：mixed 单行 47 个顶层键里图片字段只有 `mainImage` 与 `imageUrls`，当日 96/96 商品两者恒等且逐商品唯一；`_image_value()` 只读本行；S0 由 adapt 结果直写。
- **不是前端兜底图/合并串图**：`_plan_products` 只在缺图时回落该商品自己的快照图；前端 `enrichProducts` 只按 `productId` 合并，无全局兜底。
- **品牌目录没有错**：`product/list` 与数仓 `industry_knowledge_base.dws_brand_query_product_funnel_daily`（覆盖受影响商品约 75%）都不含这张图。
- **旁路写者线索**：这 868 行的 `storage_key` 全部是 `sha256(错图 URL)`，却配 47 种不同 `cached_url`（512 行 key 与 cached_url 不一致）→ 说明写入者不是常规缓存链路，疑似存在独立「图片同步」旁路写者（仓库内仅见 atlas 版本 `scripts/image_sync/atlas_browser_sync.py`，Harbor 版本不在本仓库）。

## 4. 防复发

### 4.1 共享图守卫（代码，已测试）

- 位置：`src/query_governance/relevance.py` → `ImageCacheService.prepare_products()`。
- 规则：同一图片 URL 被 ≥2 个不同 `productId` 使用 → 判定为「可疑共享图」，返回 `available=False` + `warning_code="IMAGE_URL_SHARED"`，**不下载、不复用历史缓存、不发给模型**（模型只能按文本判断），并把 warning 带进批次结果。
- 效果：即使上游再次把同一张图写进大量商品，也不会出现「用错图判相关性」和「大量商品同一张错误缩略图」；宁可退化为纯文本判断，也不产生错误结论。
- 测试：`tests/test_query_governance_image_shared_guard.py`（7 用例，含端到端护栏链）；回归 `tests/test_query_governance_relevance*.py` 等 8 个文件 124 passed、图片相关 5 个文件 21 passed。

### 4.2 治理护栏：图片可疑时禁止自动拉黑（代码，已测试）

- 数据链路：候选 `blacklist_candidates` 带 `image_warning`（asset 不可用时取 `warning_code`）→ action 带 `image_warnings`/`image_warning_messages`（**只带可疑码** `IMAGE_URL_SHARED`/`IMAGE_URL_MISMATCH`，单纯没图不带，保持历史载荷形态与自动模式）→ 计划卡片 `imageWarningCount`，并把 `executionMode` 由 `auto` 降级为 `human_approval`（`cancelable=False`、`imageSuspectCount`）→ 执行闸门 `decide_blacklist_handling()` 同样降级（`shouldExecute=False`、`shouldPersistPending=True`、`imageAutoDowngraded=True`）。
- 依据：本次事故里有 542 个无辜商品进入 `product_blacklist` 候选，若当时 `blacklist_execution_mode=auto` 就会被自动拉黑。护栏让「图片本身不可信」的结论必须人工确认。
- 关键点：**没有图的商品不降级**（`IMAGE_URL_MISSING`/`IMAGE_DOWNLOAD_FAILED` 维持旧行为），避免人工复核量暴涨；只有「图被共用/与目录不符」这类真正危险信号才拦。
- 端到端测试（`tests/test_query_governance_image_shared_guard.py`）：两个商品共用同一图 → 候选 `image_warning=IMAGE_URL_SHARED`、`image_checked=false` → action 携带告警 → `decide_blacklist_handling(..., execution_mode="auto")` 返回 `human_approval` 且 `shouldExecute=False`。

### 4.3 盘点 / 巡检（可定时，只读）

- `scripts/ops/repair_harbor_polluted_images.py inventory`：错图特征串命中、被复用的缓存对象、`storage_key` 与 `cached_url` 不一致等指标。
- `scripts/ops/audit_harbor_image_integrity.py`（新增，纯只读）：近期任务 S0 快照 + 资产表 → 共享图分组、缺图比例、资产键不一致，再用 `product/list` 抽样对图（可带像素相关，阈值 0.98）区分「上游合法复用」与「错配」，输出 `IMAGE-INTEGRITY products=… verdict=PASS|ALERT` 与 JSON，`--fail-on-alert` 可让定时任务非零退出，`--webhook-url` 可按企业微信 markdown 形态推送。
- 回放验证（证明巡检确实抓得到原事故）：`--replay-backup` 跑修复前备份 `backup-20261013T191316-11213.json` →
  `IMAGE-INTEGRITY products=19404 missing=0 shared_groups=2 shared_products=4328 verdict=ALERT`，
  其中 `[ALERT] IMAGE_URL_SHARED: 4326 个商品共用同一张图 (…/fae7537d…_xxl-1.jpg)`、`[ALERT] IMAGE_STORAGE_KEY_FOREIGN: 511 行资产记录的缓存对象与自身图片地址不一致`；第二组 2 个商品共用一张乐福鞋图，目录复核为 `legitimate_upstream_reuse`（不误报）。
- 修复后现网巡检（只读，`--env prod --brands harbor --days 3 --sample-catalog 8 --group-sample 3 --check-pixels`）：
  `IMAGE-INTEGRITY products=9203 missing=0 shared_groups=1 shared_products=2 catalog_checked=8 catalog_mismatch=0 asset_mismatch=0 verdict=PASS`（唯一共享组为上述乐福鞋合法复用）。
- 建议按日或按周在 CI / 运维定时执行巡检 + 断言 `verdict=PASS`，异常即告警。

### 4.4 残余风险与建议（需上游/产品确认）

1. **单商品独有的错图**（未被共享）无法用结构法发现——只能靠上游修复 + 周期抽样；建议把本次 2026-09-29~10-12 的 Harbor `mainImage` 污染批次反馈给搜索索引团队，定位旁路写入者与成因。
2. **历史结论文本**：已生成的 73 个计划中，基于错图得出的 reason 文本仍停留为历史记录；本次按用户要求未重跑历史相关性检测（如需可指定 Query 重跑）。
3. **`image_sha256` 列长期为空**：补齐后可支持「同字节不同 URL」的内容级去重，属后续增强。
4. 本次改动落在独立 worktree/分支，未 push、未改主目录、未动密钥。
