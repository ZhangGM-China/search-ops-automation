## 1. 产品定位

系统面向搜索运营人员，每日发现并治理影响搜索点击与转化的 Query 问题，在保证生产写操作安全、过程可追踪、结果可验证的前提下，减少人工巡检和重复处置成本。

产品覆盖三类核心工作：

- 对品牌 Top Query 做持续巡检、诊断、治理、验证与效果追踪。
- 对无结果 Query 做独立的意图诊断、知识治理、复查与人工兜底。
- 向运营人员提供品牌看板、Query 详情、治理方案、人工任务、效果观察和智能助理。

系统的成功不以“任务运行完成”为准，而以发现的问题是否得到安全处置、治理结果是否经过验证、无法自动处理的问题是否明确转交人工为准。

每日治理的分段推进、品牌关闭跳过及真实恢复进展判定见[每日治理主流程](prd/02-每日治理主流程.md)。历史缺失日期补跑须核对范围及源数据，不能用调度成功代替业务恢复。

## 2. PRD 内容边界

PRD 只描述以下产品事实：

- 业务目标与用户场景。
- 触发条件和处理对象。
- 业务输入、业务输出和业务规则。
- 状态变化、人工参与点和权限边界。
- 异常分支、降级行为和安全结果。
- 可验证的验收场景。

以下内容不得在 PRD 中展开，应引用对应文档：

- 工作流节点、类、函数、模型、提示词和代码目录。
- 数据库表结构、字段类型、索引与迁移方案。
- API 路径、请求响应字段和错误码。
- 调度器、缓存、中间件、模型接线和部署方式。
- 测试脚本、测试数量、发布命令和实现证据。

若历史 PRD 中仍存在上述技术内容，以 TSD、API 文档和当前实现为技术事实源；后续维护时迁移到对应文档，不在 PRD 中复制形成第二套口径。

## 3. 公共产品契约

所有功能 PRD 必须引用以下公共契约，不得自行重复定义同名指标或状态：

1. [术语与指标字典](prd/术语与指标字典.md)：统一日期、流量、转化、覆盖率、治理效率、成本和效果观察口径。
2. [统一状态与动作契约](prd/统一状态与动作契约.md)：统一 Query、检查项、规划轮次、动作、验证、事件、页面分类和实验观测状态。

发生冲突时按以下优先级处理：

1. 公共产品契约中的定义优先于单个功能 PRD 的重复描述。
2. 更晚生效且明确标记“替代”的已批准需求优先于旧需求。
3. 无法确认时标记为未决策问题，不在不同文档中保留互相冲突的有效口径。

## 6. 配置型规则的写法

阈值、数量、时间窗口、执行额度、频率、超时、重试次数、样本规模等可能随品牌或环境调整的数值，PRD 不得写成固定产品常量。

功能 PRD 必须说明：

- 配置项控制的业务含义。
- 配置适用范围，例如全局、品牌、检查项或动作类型。
- 配置来源的优先级，以[术语与指标字典](prd/术语与指标字典.md)中的“配置值”定义为准。
- 配置缺失、无效或冲突时的安全行为。

默认安全行为遵循以下原则：

- 缺少判断阈值时，不得把未知风险判为健康，也不得自动执行生产写动作。
- 缺少动作权限或额度时，保留诊断与建议，动作转为待人工处理或禁止执行。
- 缺少统计窗口时，不生成需要该窗口支持的对比结论，并明确标记数据不足。
- 缺少展示配置时，不得改变底层业务状态；页面应展示可理解的缺省说明。

固定数值只有在法律、安全或已经批准的不可配置业务契约中才允许出现，并必须说明固定原因。

## 7. 功能 PRD 标准结构

新增或重写功能 PRD 时，至少包含：

1. 创建时间与最后更新时间。
2. 业务目标与用户场景。
3. 适用范围与非目标。
4. 触发条件。
5. 业务输入及输入有效性要求。
6. 业务规则与可配置规则说明。
7. 业务输出。
8. 状态变化和人工参与点。
9. 异常、降级与安全行为。
10. Given / When / Then 验收场景。
11. 依赖的公共契约、相关 PRD、TSD 和 API 文档。
12. 未决策问题。

单篇文档超过一个清晰业务闭环时应继续拆分；拆分后的子文档必须由总纲或上级功能文档导航。

## 8. 文档维护规则

### 8.1 日期记录

每份需要维护日期的 PRD，在标题后只记录创建时间和最后更新时间：

| 字段 | 规则 |
| --- | --- |
| 创建时间 | 文档首次建立时确定；重命名或拆分不改变原始创建时间 |
| 最后更新时间 | 业务口径发生实质变化时更新；仅修复链接、排版或索引时可不改变 |

### 8.2 内容维护约束

- 同一业务概念只保留一个权威定义，其他文档通过链接引用。
- 不使用“明显”“合理”“稳定”“必要时”“高置信度”等不可验收表述，除非同时说明判断依据来自配置、确定性规则或需人工判断。
- 业务状态名称必须引用[统一状态与动作契约](prd/统一状态与动作契约.md)。确需新增状态时，先更新公共契约，再使用新状态。
- 指标名称、分子、分母、时间窗口、空值和聚合方式必须引用[术语与指标字典](prd/术语与指标字典.md)。
- 历史兼容字段必须同时标记“字段名”和“当前业务语义”，不得根据旧字段名恢复旧口径。
- 未实现需求不得写成当前事实；已实现能力也不得只凭代码存在宣称完成，必须有对应验收证据。

## 9. 当前需求优先级

当前产品主线优先保证：

1. Top Query 每日任务按“采集 S0 → 召回检查 → 排序治理 → 相关性检测 → 主链结束”的固定顺序形成闭环。
2. Query、检查项、动作、验证结果和页面分类之间保持一致。
3. 所有生产写操作经过权限、执行模式、审计、验证和回滚边界。
4. 指标口径、成本口径和效果观察口径可由开发者与 AI 唯一理解。
5. 无法自动处理或证据不足的问题明确进入人工处理，不以默认健康或补零掩盖。
6. 手工相关性检测与治理主链隔离：仅保存检测任务状态与结果，不复用历史结论，不创建拉黑、KG 或治理动作。
7. 每个 Query 已判定不相关的商品在检测后独立进入拉黑处理，不等待根因分析，不因根因未知或 KG 方案失败而漏掉拉黑。Agent 与对应运营工具取最严格执行模式（禁止执行 > 确认后执行 > 自动执行）；仅两者均为自动时自动写入。独立相关性治理 Agent 同时负责根因分组、生成一条或多条可一键执行的 KG 修复方案，不再生成或执行商品拉黑动作。KG 方案按同一两层规则执行，确认模式等待人工操作。当日调整收口后统一 retag，30 分钟后在执行概览“相关性”卡片展示验证结果。召回数量异常只由 KG Agent 处理。治理方案按策略分组展示错误商品，每个商品只出现一次；明确原因组优先，未覆盖商品仍保留在待复核组，商品操作沿用独立拉黑动作。

相关性治理策略正文仅展示治理动作或人工复核提示，不重复展示分组错误原因和根因结论；错误原因在对应错误商品卡片中展示。

## 10. 非目标

- PRD 不作为源码、数据库或接口字段的替代文档。
- PRD 不记录一次性调试过程、测试通过数量或生产连接信息。
- PRD 不为尚未确认的未来能力虚构状态、页面或交付事实。
- 不因文档重构改变现有生产权限、安全红线或数据源只读边界。

相关性 KG 策略生成前必须查询原词标签、双向关系及维度；复合短语缺失时继续核查等价根标签和短语治理路径。动作格式或证据校验失败时最多修复一次，仍失败则保留原始动作、查询证据和失败原因，显示“需人工复核”，不得显示“无需处理”或允许执行空策略。
