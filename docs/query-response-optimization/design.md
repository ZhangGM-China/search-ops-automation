# Query 看板响应优化设计

## 目标

降低生产 Query 看板首屏和翻页接口的响应时间，消除“返回分页、后端全量计算”的伪分页，并让两个 Backend Pod 共享热点读取缓存。

## 范围

本阶段覆盖 Query rail 列表接口、品牌总览接口、Query 详情读取前的请求边界、API 请求耗时观测和健康检查隔离。生产 Redis 实例由部署环境提供，应用通过配置连接；本阶段不创建或修改生产基础设施。

## 数据流

- `filter=all`：先查询批次、总数和当前页任务；只读取当前页步骤和指标；统计优先复用已物化摘要。
- 其他筛选：保留正确性优先的全量筛选路径，先增加耗时观测；后续可基于投影表继续优化。
- 批次即使存在部分 Query 错误，也要持久化带错误统计的 overview 摘要，避免请求回退到全量步骤聚合。
- 全量兼容路径按小批次读取步骤，规避 MySQL 对大 `IN (...)` 加载 `result_json` 的慢执行计划。
- 候选指标按 `batch_id + brand + query_text` 查询，并由发布入口补齐对应复合索引。
- API 缓存：优先读取 Redis，Redis 不可用时回退进程内缓存和数据库；写入 Redis 失败不影响请求成功。
- 缓存 key 包含接口版本、品牌、业务日期、页码、页大小和筛选条件，避免跨版本和跨筛选污染。
- `current-result-count` 使用线程池可调度的同步路由，避免同步数据库/HTTP 调用阻塞单 Worker 事件循环，并复用同一共享缓存。
- 当前日期缓存短 TTL，历史业务日期使用更长 TTL；写路径清理相关缓存。

## Redis 边界

新增轻量 Redis 适配器，支持连接 URL、连接超时、读写超时和 key 前缀配置。适配器只负责 JSON value 的 get/set/delete，不把 Redis 客户端泄露到业务层。未配置 URL 或连接失败时返回 cache miss，并记录一次可采样的 warning。

## 稳定性

- `/api/health/live` 保持纯进程检查。
- `/api/health/ready` 才执行有界数据库检查。
- API 继续通过现有 `Server-Timing` 暴露总耗时；不记录 Token、完整 Query 或数据库凭据。Redis 失败仅记录一次脱敏 warning。
- 实时结果缓存只保存结果投影，不保存 task id；响应时恢复当前请求的 task id，避免相同 Query 跨任务串数据。
- 不调整生产副本、探针阈值或 worker 数量，先用观测验证后续动作。

## 验收标准

- `filter=all` 的列表读取只加载当前页任务和步骤，返回契约保持不变。
- 同一缓存 key 的第二次请求可跨进程复用 Redis 数据；Redis 不可用时接口仍返回正确结果。
- 前端切换路由或页码时会取消过期请求，不重复加载详情。
- 相关单元、API 和前端 Hook 测试通过；生产只读验收可观察 cache hit、接口耗时和 Pod 探针状态。
